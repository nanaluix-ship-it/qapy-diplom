# План автоматизации

## Что буду тестировать

Сервис покупки туров: приложение aqa-shop.jar (порт 8080),
эмулятор банковских сервисов gate-simulator (порт 9999), СУБД.
Покупку можно сделать двумя способами - обычной оплатой по карте
(Payment Gate) и в кредит (Credit Gate). Приложение пересылает данные
карты банковским сервисам, а в свою БД пишет только информацию
о результате операции - сохранять данные карт оно не должно.

Тестирую оба способа покупки, плюс смотрю, что реально
записывается в базу. Приложение поддерживает MySQL и PostgreSQL,
я выбрала и использую MySQL.

## Какие сценарии буду автоматизировать

Сначала позитивные:
- покупка по дебетовой карте со статусом APPROVED (карта 4444 4444 4444 4441
  из data.json) - проверю сообщение об успехе на странице и запись
  в таблице payment_entity;
- покупка в кредит той же картой - проверю кредитный сценарий и запись
  в credit_request_entity.

Потом негативные:
- карта со статусом DECLINED (4444 4444 4444 4442) - оплата должна
  отклониться, и это должно отразиться в БД;
- пустые поля формы;
- невалидный номер карты (не 16 цифр, буквы, случайный номер - эмулятор
  для таких карт возвращает 400);
- невалидный месяц (00 и 13) и год из прошлого;
- невалидный CVV (две цифры, буквы, пустое поле);
- некорректное имя владельца (кириллица, цифры, спецсимволы, очень
  длинная строка);
- отдельной проверкой уточню, что номер карты нигде не сохраняется
  в базе - это прямо требование задания.

Помимо UI сделаю несколько API-проверок напрямую к эмулятору
(POST на /payment и /credit).

И финальный блок - SQL-проверки из тестов: сверю, что статус и сумма
записи в БД соответствуют тому, что показал интерфейс.

## Инструменты

Пишу на Python, потому что курс проходил на нём:
- pytest - тесты;
- Selenium WebDriver - UI-тесты (это требование задания);
- allure-pytest - отчёты (тоже требование задания);
- docker-compose - поднимаю MySQL и эмулятор одной командой,
  чтобы проект запускался у любого человека из репозитория;
- mysql-connector-python и psycopg2 - для запросов к СУБД из тестов;
- requests - для API-проверок;
- Faker - генерировать невалидные данные.

## Риски
- поскольку нет четкого ТЗ о том, как должны валидироваться поля, границы 
(например, до какого года принимать карту) буду определять по фактическому поведению.
- Инфраструктурные проблемы: Docker, порты, скорость старта СУБД -
  на отладку этого может уйти больше времени, чем кажется.
- Часть проблем с UI будет из-за локаторов - заранее беру время
  на их поиск.
