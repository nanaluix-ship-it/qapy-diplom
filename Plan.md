# План автоматизации

## Что буду тестировать

Сервис покупки туров: приложение aqa-shop.jar (порт 8080),
эмулятор банковских сервисов gate-simulator (порт 9999), СУБД.
Покупку можно сделать двумя способами — обычной оплатой по карте
(Payment Gate) и в кредит (Credit Gate). Приложение пересылает данные
карты банковским сервисам, а в свою БД пишет только информацию
о результате операции — сохранять данные карт оно не должно.

Тестирую оба способа покупки, плюс смотрю, что реально
записывается в базу. Приложение поддерживает MySQL и PostgreSQL,
основная конфигурация — MySQL.

## Какие сценарии буду автоматизировать

Сначала позитивные:
- покупка по дебетовой карте со статусом APPROVED (карта 4444 4444 4444 4441
  из data.json) — проверю сообщение об успехе на странице и запись
  в таблице payment_entity (статус и сумма);
- покупка в кредит той же картой — проверю кредитный сценарий и запись
  в credit_request_entity;
- связь order_entity с операциями обоих типов;
- граничные значения месяца/года и корректные граничные CVC.

Потом негативные:
- карта со статусом DECLINED (4444 4444 4444 4442) — оплата должна
  отклониться, и это должно отразиться в БД;
- пустые поля формы (обе формы);
- невалидный номер карты (не 16 цифр, буквы);
- невалидный месяц (00 и 13), год из прошлого и сильно будущий;
- невалидный CVC (короткие значения, буквы, пустое поле);
- некорректное имя владельца (кириллица, цифры, спецсимволы,
  очень длинная строка);
- отдельной проверкой уточню, что номер карты нигде не сохраняется
  в базе — это прямо требование задания (проверка по всем колонкам
  созданных записей, в двух видах записи номера).

Помимо UI сделаю API-проверки в двух уровнях: к эмулятору шлюза
(POST на /payment и /credit — поведении DECLINED и незнакомой карты)
и к собственному API приложения (POST на /api/v1/pay и /api/v1/credit,
включая обработку невалидного тела запроса).

Финальный блок — SQL-проверки из тестов: сверю, что статус и сумма
записи в БД соответствуют тому, что показал интерфейс; проверю,
что заказ не создаётся при отказе банка и что ссылки между таблицами
не нарушаются.

## Инструменты

Пишу на Python, потому что курс проходил на нём:
- pytest — тесты;
- Selenium WebDriver — UI-тесты (это требование задания);
- allure-pytest — отчёты (тоже требование задания);
- docker-compose — поднимаю MySQL, эмулятор и приложение одной командой,
  чтобы проект запускался у любого человека из репозитория;
- mysql-connector-python — для запросов к СУБД из тестов;
- requests — для API-проверок;
- Faker — генерировать данные владельца карты.

## Риски
- Поскольку нет чёткого ТЗ о том, как должны валидироваться поля,
  границы (например, до какого года принимать карту) буду определять
  по фактическому поведению.
- Нестабильность ответов эмулятора шлюза-заглушки: отдельные тесты
  могут давать флаки по таймаутам, не связанные с дефектами приложения.
- Инфраструктурные проблемы: Docker, порты, скорость старта СУБД —
  на отладку этого может уйти больше времени, чем кажется.
- Часть проблем с UI будет из-за локаторов — заранее беру время
  на их поиск.
